Event ID 1102: the Security log was cleared

What Event ID 1102 means when the Windows Security log is cleared, how to tell admin housekeeping from an attacker hiding tracks, and how to recover the events.

Updated 2026-11-11 · 7 min read

An alert says Event ID 1102 on a file server: "The audit log was cleared." You open Event Viewer and the Security log is almost empty. The 1102 record sits near the top, and everything before it is gone from that machine. That is exactly why this event matters. Someone with admin rights decided the history on that host should not exist anymore.

Sometimes that someone is a sysadmin tidying up. Often enough it is the last step of an intrusion. Here is how to tell which, and how to get back what the clear tried to erase.

If you already have the events exported, Windows Event Triage flags the clear and the activity around it in one pass.

What does Event ID 1102 mean?

1102 is written by Microsoft-Windows-Eventlog into the Security log at the moment that log is cleared. It is logged no matter how audit policy is set, so you cannot turn it off by disabling an audit category. It is the first entry in the fresh log.

The record is short. The useful part is the Subject:

The audit log was cleared.
Subject:
    Security ID:    CORP\support_adm
    Account Name:   support_adm
    Domain Name:    CORP
    Logon ID:       0x3E7A21F

The account name tells you who did it. The Logon ID is the part most people skip, and it is the most valuable field in the event. More on that below.

Clearing other logs leaves a different trace: Event ID 104 in the System log ("The System log file was cleared"), with the name of the cleared log in the event data. An attacker who clears everything usually leaves one 1102 and several 104s within a few seconds of each other.

Is Event ID 1102 malicious or a false positive?

There are honest reasons a log gets cleared: an admin troubleshooting an audit setting who wanted a clean slate, a build script on a new server, a third-party cleanup tool someone installed. None of those is good practice on a production server, but none is an attack.

The questions I ask, in this order:

  1. Who cleared it? A named admin account is a starting point. A service account, a user account that should not have admin rights, or a generic local Administrator is a bad sign.
  2. Was there a change ticket? Ask the account owner directly. If they did not clear it, or cannot say why, stop treating it as housekeeping.
  3. What host and when? A domain controller cleared at 02:40 on a Sunday is a different conversation from a test VM during working hours.
  4. What else was cleared? One Security log clear during troubleshooting is plausible. Security, System, Windows PowerShell and Sysmon all cleared within a minute is not troubleshooting.

Treat it as hostile until explained if the clear came from the command line, touched several logs, happened on a domain controller, or followed new services, new admin accounts or remote logons from an unusual source.

How was the log cleared?

The method tells you something about the person. Event Viewer's "Clear Log" is what an admin clicks. Attackers script it, because it is one line:

wevtutil cl Security
wevtutil cl System
Clear-EventLog -LogName Security, System, Application

If you collect process creation (Event ID 4688 with command lines, or Sysmon Event ID 1), search for wevtutil with the cl argument and for Clear-EventLog. The 4688 for the clear itself may be gone with the local log, which is the next problem.

A careful attacker can avoid 1102 entirely, for example by stopping the event log service or tampering with it before deleting files. So the absence of 1102 is not proof of a clean host. A sudden gap in a host's logs in your SIEM, or Event ID 1100 (event logging service shut down) without a reboot, deserves the same attention.

How do I find what happened before the log was cleared?

The local log is gone. The events are often not.

1. Your SIEM or Windows Event Forwarding copy

If the host forwards its logs, everything up to the clear is already off the box. This is where the Logon ID earns its keep: search for the 4624 logon on that host whose New Logon > Logon ID matches the Logon ID in the 1102. That gives you the logon type and source IP of the session that did the clearing, and you can follow the same Logon ID through 4688, 4672 and other events to see what that session did before it wiped the log.

In Microsoft Sentinel, start with:

SecurityEvent
| where TimeGenerated > ago(30d)
| where EventID == 1102
| project TimeGenerated, Computer, Account, EventData
| order by TimeGenerated desc

For the other logs, the 104 events land in the Event table:

Event
| where TimeGenerated > ago(30d)
| where EventLog == "System" and EventID == 104
| project TimeGenerated, Computer, RenderedDescription, EventData

Depending on your connector, the subject fields for 1102 may only be inside EventData rather than in Account, so check the raw XML before assuming the field is empty.

2. On the host itself

Pull the clear events and who did them:

Get-WinEvent -FilterHashtable @{LogName='Security'; Id=1102} |
  ForEach-Object {
    $x = ([xml]$_.ToXml()).Event.UserData.LogFileCleared
    [pscustomobject]@{ Time=$_.TimeCreated; User="$($x.SubjectDomainName)\$($x.SubjectUserName)"; LogonId=$x.SubjectLogonId }
  }

Get-WinEvent -FilterHashtable @{LogName='System'; Id=104} |
  Select-Object TimeCreated, Message

A tip juniors rarely know: if the Security log is configured to archive when full, older events sit in files named Archive-Security-*.evtx in %SystemRoot%\System32\winevt\Logs. Clearing the live log does not delete those. Check the folder before you assume nothing survived, and copy anything you find off the host before you work with it.

3. Other sources that don't live in the Security log

EDR telemetry, firewall and VPN logs, the domain controller's own logs for authentications from that host, and logs that weren't cleared. Attackers often miss one, such as Microsoft-Windows-PowerShell/Operational or a Sysmon log they didn't know was there.

What to do after confirming an unexplained 1102

  1. Preserve first. Export the remaining logs and any archive files from the host before anyone reboots or reimages it.
  2. Treat the clearing account as compromised. Reset its password, revoke its sessions, and check where else it logged on recently.
  3. Scope the session. Using the Logon ID and your SIEM copy, list what ran, which services were installed (7045), and whether accounts or group memberships changed. The new admin account detection guide covers the 4720 and 4732 checks. If you find encoded PowerShell in the session, decode it before deciding what it did.
  4. Check neighbouring hosts. Clearing logs is rarely done on only one machine. Search the same account and time window across the estate.
  5. Fix the gap. If this host was not forwarding logs, the clear worked. Get it forwarding, and make sure log clearing alerts in real time.

FAQ

Can I stop admins from clearing the Security log?

The right to manage the audit log is granted by the "Manage auditing and security log" user right, which local administrators hold by default. You can restrict who has it, but a determined admin can grant it back. The practical control is forwarding logs off the host so that clearing the local copy loses nothing.

Why does the 1102 show a different account than I expected?

The Subject is the account whose session issued the clear. If a tool running as a service or scheduled task did it, you may see that service's account or SYSTEM rather than the person behind it. Follow the Logon ID back to the logon and the process that started it.

What MITRE ATT&CK technique is log clearing?

T1070.001, Clear Windows Event Logs, under Indicator Removal in the Defense Evasion tactic. Tagging the alert with it helps when you report the incident or map detection coverage.

Is Event ID 1102 the same on Windows Server and Windows 10 or 11?

Yes. The event ID, the message and the Subject fields are the same across supported versions of Windows client and server, so the same query and alert work everywhere.
