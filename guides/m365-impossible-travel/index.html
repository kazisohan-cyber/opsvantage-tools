Microsoft 365 impossible travel: investigate and respond

What triggers impossible travel and atypical travel alerts in Microsoft 365 and Entra ID, how to rule out VPN false positives, the sign-in log fields to check, and the response steps when it is real.

Updated 2026-11-03 · 9 min read

The alert says a user signed in from Singapore at 09:00 and from Lagos at 10:10. Nobody flies that fast. Most of the time the explanation is boring: a VPN, a mobile carrier routing traffic abroad, a cloud desktop in another region. But the one that isn't boring is often the first sign of business email compromise, and by the time anyone notices, there's already a forwarding rule on the mailbox.

That's why a Microsoft 365 impossible travel alert deserves five careful minutes rather than a reflexive close. This is how to investigate it and respond.

Where the alert comes from

  • Microsoft Defender for Cloud Apps (and Defender XDR): the "Impossible travel" anomaly policy, which learns each user's behaviour first.
  • Microsoft Entra ID Protection (P2): the "Atypical travel" sign-in risk detection, which raises the sign-in or user risk.
  • Your own rules in Sentinel or another SIEM built on SigninLogs.

Common false positives

  • VPNs and secure web gateways (Zscaler, Netskope, consumer VPNs) that exit in another country.
  • Mobile carriers that route data through a regional hub in another country.
  • Cloud-hosted desktops (AVD, Windows 365, Citrix) in a different region from the user's laptop.
  • Background clients such as Outlook mobile, whose sign-ins can come from Microsoft's own infrastructure.

The test: is the "far away" IP owned by a known VPN, carrier or cloud provider your organisation uses, and does the session look like the user's usual device?

What to check in the sign-in logs

Entra admin center > Identity > Monitoring & health > Sign-in logs, filter by the user and the alert window.

FieldSuspicious when
IP address and ASNHosting provider, VPS or anonymiser you don't use; IP seen across many unrelated tenants
ApplicationOfficeHome or Exchange Online straight after a phishing email; Azure portal or PowerShell for a non-admin
Client app / user agentLegacy protocols (IMAP, SMTP), python-requests, axios, an unusual browser
Authentication detailsMFA satisfied "by claim in the token" from a new device (token theft), or many MFA denials before a success (push bombing)
DeviceNot compliant, not joined, new OS
Conditional Access"Not applied": a gap in your policies

Adversary-in-the-middle phishing (Evilginx-style kits) steals the session cookie after the user completes MFA. The giveaway is a sign-in from a hosting provider IP, seconds after the user's real sign-in, with MFA marked as already satisfied.

If I can only look at two things, it's the ASN of the far-away IP and the authentication details of that sign-in. A residential or mobile ISP in a country the user visits is usually travel or a carrier. A hosting provider with "MFA requirement satisfied by claim in the token" on a device the user has never used is a stolen session until proven otherwise.

KQL for Sentinel

SigninLogs
| where TimeGenerated > ago(2d) and UserPrincipalName =~ "user@contoso.com"
| project TimeGenerated, IPAddress, Country = tostring(LocationDetails.countryOrRegion),
          AppDisplayName, ClientAppUsed, UserAgent, ResultType, AuthenticationRequirement,
          ConditionalAccessStatus, RiskLevelDuringSignIn
| order by TimeGenerated asc

If it is real: respond in this order

  1. Revoke sessions so stolen tokens stop working: user > Revoke sessions, or Revoke-MgUserSignInSession -UserId user@contoso.com.
  2. Reset the password and require MFA re-registration if a method may have been added by the attacker. Remove unknown authentication methods.
  3. Check the mailbox for new inbox rules (forwarding, moving to RSS Feeds or Archive, deleting), external forwarding and sent items. BEC attackers set these up within minutes.
  4. Check app consents granted by the user (Enterprise applications > User consent) and revoke unknown ones.
  5. Search the audit log for what the session did: file downloads, sharing links, mail sent.
  6. Close the gap: require MFA for all users, block legacy authentication, and consider phishing-resistant MFA (passkeys) for admins and finance.

Prevent the next one

Most impossible travel incidents trace back to the same few gaps: users without MFA, legacy authentication still allowed, risky app consent open to everyone, and no Conditional Access for risky sign-ins. A posture scan finds all of them in a minute.

FAQ

Does an impossible travel alert mean the account is compromised?

Not by itself. It means two sign-ins don't fit together geographically. Confirm with the IP owner, the device, the authentication details and what the session did before deciding.

How do I reduce VPN false positives?

Tell the detection about your egress IPs. In Defender for Cloud Apps, add your VPN and proxy ranges as IP address ranges with a corporate or VPN tag; in Entra ID, define them as trusted named locations. Detections then stop treating that traffic as travel.

Is resetting the password enough?

No. Existing sessions and refresh tokens can keep working after a password change. Revoke sessions first, then reset the password, then check the mailbox for rules and forwarding the attacker may have added.

What's the difference between impossible travel and atypical travel?

They describe the same idea from two products: impossible travel is the Defender for Cloud Apps anomaly, atypical travel is the Entra ID Protection risk detection. Either way, the investigation steps above are the same.
