Event ID 4625: failed logons explained

What Windows Security Event 4625 means, how to read the logon type and status codes, how to tell brute force from password spraying, and what to do next.

Updated 2026-11-03 · 9 min read

It's late, and the SIEM says one account has 40 failed logons in five minutes. Before escalating, open one of the Event ID 4625 records. The fields inside tell you, usually within a minute, whether you're looking at someone guessing a password, a password spray across the whole company, or a laptop with a stale password hammering a file share. That last one is far more common than anyone likes to admit, and it buries the real attacks in noise.

4625 is written to the Windows Security log every time an account fails to log on. Here's how to read it and decide what to do.

The fields that matter

FieldWhat it tells you
Account For Which Logon Failed > Account NameThe account being tried. Ignore the Subject section, which is usually the local system.
Logon TypeHow the logon was attempted. See the table below.
Status / Sub StatusWhy it failed. The Sub Status is the precise reason.
Source Network AddressThe IP the attempt came from. - or 127.0.0.1 means local.
Workstation NameThe name the client claimed. Attack tools often send random or blank names.
Authentication PackageNTLM or Kerberos. NTLM from unexpected hosts deserves a second look.

Logon types you will see in 4625

TypeMeaningTypical cause of failures
2Interactive (keyboard at the machine)User typo, someone at the console
3Network (SMB, file shares, many RDP attempts with NLA)Brute force over SMB or RDP, stale mapped drives
4Batch (scheduled task)A task still running with an old password
5ServiceA service account whose password changed
7UnlockUser mistyping at the lock screen
8Network cleartext (IIS basic auth)Password spraying against web apps
10Remote interactive (RDP without NLA)RDP brute force from the internet
11Cached interactiveLaptop off the network with an old cached password

Status and Sub Status codes

CodeMeaningRead it as
0xC000006ACorrect username, wrong passwordSomeone knows a valid account name
0xC0000064Username does not existGuessing names: spraying or enumeration
0xC0000234Account is locked outAttempts continuing after lockout
0xC0000072Account is disabledSomeone trying a leaver's account
0xC0000071Password expiredUsually a real user
0xC0000193Account expiredContractor or leaver account
0xC000006F / 0xC0000070Outside allowed hours / not allowed from this workstationPolicy working as designed
0xC000015BLogon type not grantedAccount blocked from RDP or local logon by policy
0xC0000133Clock out of sync with the domain controllerTime sync problem, not an attack

0xC000006D in the Status field is a generic "bad username or password"; always read the Sub Status for the real reason.

Brute force or password spraying?

  • Brute force: one account, many failures, usually from one or a few IPs. Rule of thumb: 10 or more failures for the same account within 10 minutes.
  • Password spraying: one source, many different accounts, a few attempts each, often with Sub Status 0xC0000064 for names that don't exist. Five or more distinct accounts from one IP is worth an alert.
  • Misconfiguration: the same account failing every few minutes around the clock, from an internal server, with logon type 4 or 5. That is an old password in a task, service or mapped drive.

My order of checks is always the same: Sub Status first (is the account even real?), then the source IP (internal server or the internet?), then whether a success followed. Most 4625 floods are settled by the first two. A burst of 0xC000006A from an internal file server at a steady rhythm is a saved credential; the same code from a hosting provider's IP is someone who already knows a valid username.

The one pattern to never ignore: a run of 4625 failures for an account followed by a 4624 success for the same account from the same source. Treat it as a compromised password until proven otherwise.

Pull the events quickly

PowerShell on the server

Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625; StartTime=(Get-Date).AddHours(-24)} |
  ForEach-Object {
    $x = [xml]$_.ToXml()
    $d = @{}; $x.Event.EventData.Data | ForEach-Object { $d[$_.Name] = $_.'#text' }
    [pscustomobject]@{ Time=$_.TimeCreated; User=$d.TargetUserName; IP=$d.IpAddress; Type=$d.LogonType; SubStatus=$d.SubStatus }
  } | Group-Object User, IP | Sort-Object Count -Descending | Select-Object -First 20 Count, Name

Microsoft Sentinel (KQL)

SecurityEvent
| where TimeGenerated > ago(24h) and EventID == 4625
| summarize Failures = count(), Accounts = dcount(TargetAccount) by IpAddress, bin(TimeGenerated, 10m)
| where Failures >= 10 or Accounts >= 5
| order by Failures desc

What to do next

  1. Check for a success. Search 4624 for the same account and IP right after the failures.
  2. Look up the source IP. Public IP on RDP or SMB means the service is exposed to the internet; that is the real finding.
  3. Block or restrict. Block the IP at the firewall, put RDP behind a VPN or gateway with MFA, and make sure account lockout policy is set.
  4. If a success happened: reset the password, sign the user out everywhere, review what the session did (4688 process creation, new services 7045, new users 4720).
  5. If it is a stale credential: find the task, service or mapped drive on the source host and update it, or the noise will hide a real attack later.

FAQ

Is a single Event ID 4625 a security problem?

No. One or two failures followed by a success from the user's usual machine is someone mistyping. It becomes interesting when the volume, the number of different accounts, or the source IP doesn't fit how that user normally works.

Why is the Source Network Address "-"?

The attempt didn't come over the network: someone tried at the console, the lock screen, or a local process tried to authenticate. Look at the logon type and the process name fields instead.

What's the difference between 4625, 4771 and 4776?

4625 is logged on the machine where the logon was attempted. For domain accounts, the domain controller also records the failure: 4771 for Kerberos pre-authentication, 4776 for NTLM. When you hunt for password spraying across a domain, the DC events give you the wider view.

How many failed logons should trigger an alert?

A sensible starting point is 10 failures for one account within 10 minutes, or 5 different accounts failing from one source. Tune it after a week: if service accounts with stale passwords keep firing it, fix those accounts rather than raising the threshold.
