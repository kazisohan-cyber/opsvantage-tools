Email Header Analyzer

What it reads

  • Authentication-Results (and ARC copies), Received-SPF and DKIM-Signature, for SPF, DKIM, DMARC and Microsoft's composite authentication.
  • Received headers, oldest first, for the route and the delay at each hop. The IP inside the brackets is the one the receiving server saw on the connection, so it wins over the name the sender typed.
  • From, Reply-To, Return-Path and Message-ID, compared with each other and with a list of well-known brands.
  • With a whole .eml: every link (the address shown and the address it really goes to, with Microsoft Safe Links unwrapped) and every attachment (name, size, SHA-256 and risky types such as HTML, ISO, LNK or macro-enabled Office files).

How the verdict is reached

Each signal adds or removes points. DMARC fail adds 30, SPF fail 25, a Reply-To on another organisation's domain 25, a brand in the display name sent from someone else's domain 25; DMARC pass removes 15. A total of 45 or more is malicious, 18 or more suspicious, and -15 or less benign. Brand impersonation never scores below suspicious, because a phisher's own domain can pass SPF, DKIM and DMARC perfectly. Risky attachments, link text that hides a different domain, or links the brand checks block raise the verdict further.

Limits

Headers added by your own mail system are trusted as written; anything before the first server you control could be forged. A clean result means these patterns are absent, not that the email is safe.

Grades: A from 90, B from 75, C from 60, D from 40, F below. The SPF lookup count follows RFC 7208: every include, a, mx, ptr, exists and redirect costs one, nested includes count too, and more than 10 makes receivers return a permanent error.

Limits

DKIM can only be found on selectors the checker knows or you type in; a domain can sign with a selector it can't guess. The checker reads published records. It can't tell whether your sending services actually sign and align, which only a real message (or your DMARC reports) shows.

Windows Event Triage

Input

Event Viewer CSV or XML, PowerShell Export-Csv, wevtutil /f:xml, and SIEM exports in CSV or JSON from Microsoft Sentinel, Splunk and Elastic (winlogbeat / ECS). Field names from those formats are mapped to the Windows ones the rules use.

Limits

The rules only see what was exported. Many attacks show up mainly in Sysmon or PowerShell (4104) logs, so include those when you can. Thresholds are deliberately simple; a quiet attacker can stay under them.

Distances use the coordinates in the export when present, otherwise a central point for each country, so travel speeds are estimates. VPNs and mobile networks cause false impossible-travel alerts; confirm with the user.

IOC Extractor

Finds IPv4 and IPv6 addresses, domains, URLs, email addresses, MD5, SHA-1 and SHA-256 hashes, CVEs, file names and paths, registry keys, ASNs and Bitcoin addresses, including defanged forms such as hxxp, [.], (dot) and (at). Domains must end in a real top-level domain from the IANA list, and log field names, version numbers and clock times are skipped. A name like invoice.pdf goes to the file list rather than the domain list; write it defanged (invoice[.]pdf) if you mean the host.

Phishing Link Unwrapper

Each link is unwrapped one layer at a time: Microsoft Defender Safe Links (url=), Proofpoint URL Defense v1, v2 (-XX hex and _ for slashes) and v3 (the * markers are filled in from the Base64 block after __;), Barracuda, Symantec, Google, Facebook, LinkedIn and Slack redirects, Base64-encoded URLs, and finally any query parameter that is itself a full URL. OAuth redirect_uri is deliberately not followed. Mimecast, Cisco and link shorteners keep the destination on their servers, so the tool says so and marks the link "be careful" instead of guessing.

The destination then goes through the same brand and lookalike checks as the IOC Triage extension: well-known brands on domains they don't own, mixed alphabets and punycode, free hosting, bare IPs, unusual ports, plain HTTP, user@host tricks, long subdomain chains and links straight to HTML, ISO or executable files.

Hunting Query Generator

Indicators are extracted the same way as the IOC Extractor, refanged and de-duplicated; domains inside URLs are added to the domain search and private IPs are dropped unless you include them. Queries are generated from fixed templates: Microsoft KQL uses union isfuzzy=true so missing tables are skipped, Splunk uses CIM field names plus a tstats search on the Network_Traffic data model, CrowdStrike uses LogScale in() on sensor events, and Elastic uses KQL on ECS fields. Field names differ between environments, so treat the queries as a strong starting point and check them against your own data.

CVE Prioritizer

PriorityRule
Patch nowOn the CISA Known Exploited Vulnerabilities list
HighEPSS 10% or more, or CVSS 9.0+ with EPSS at least 1%
MediumCVSS 7.0 or more
LowEverything else, including CVEs with no score yet

EPSS is the probability, from FIRST, that a CVE is exploited in the next 30 days. CVSS comes from the CVE.org record: the CNA score when present (CVSS 3.1 preferred, then 4.0, 3.0, 2.0), otherwise the CISA ADP enrichment. Up to 100 CVEs per run. Priority describes the vulnerability, not your exposure: an internet-facing server with a Medium CVE can still come first.

Payload Decoder

Each pass looks for, in order: a PowerShell -EncodedCommand argument, a FromBase64String() or similar call, a whole hex string, a whole Base64 string, URL encoding, HTML entities, character codes, reversed text, and the longest Base64 run inside other text. Decoded bytes are checked for gzip, zlib and raw deflate and for UTF-16LE text, and a layer is only accepted when it produces readable text or a recognised file type. It stops after ten layers. The result is scanned for risky behaviour (download cradles, Invoke-Expression, hidden windows, AMSI tampering, Mimikatz, abused Windows tools, Defender changes, backup deletion, persistence) and for indicators. Custom ciphers such as XOR are not attempted.

JWT Token Decoder

The header and payload are Base64url-decoded and explained. For Microsoft Entra ID tokens it names well-known Microsoft client apps and APIs, maps the wids claim to directory roles, reads amr for MFA, and flags privileged roles, powerful scopes, public command-line clients often used in device-code phishing, lifetimes over two days and unsigned (alg: none) tokens. The signature is not verified. Tokens are credentials: prefer expired ones, and the page clears the box when you leave.

M365 Posture Scanner

Signs in with delegated, read-only Microsoft Graph permissions and checks MFA coverage, admin roles, Conditional Access, legacy authentication, app consents, guests, stale and unlicensed accounts, licences and email domain security. Checks that need an Entra ID P1 or P2 licence the tenant doesn't have are marked not checked instead of guessed. Shared mailboxes and other unlicensed accounts are counted separately, so they don't skew the MFA figures. The permissions it asks for, and how to remove it, are listed in the privacy policy.
